# Linty: organic launch plan

Prepared 21 September 2026. Budget: founder-led organic growth, with little or no paid spend. This is a strategy and content proposal; no posts, outreach, product changes, or deployments have been made.

Launch the existing Linty app to a narrow audience, learn whether they keep using it, and use that evidence to expand. Start with developers and indie builders on Apple Silicon who regularly write prompts, issue descriptions, and project updates. Keep the core app free during this experiment. A separate Lite app would split attention before we know what prevents adoption.

The initial positioning to test is: **“Turn spoken thoughts into text, right where you work. Free, on-device dictation for your Mac.”** For developer channels, lead with **“Speak your next prompt.”** Follow with the actual workflow: choose a language, hold a key, speak, release to paste. The supporting reasons to try Linty are local speech recognition, optional local English cleanup, no account or API key, and free downloadable software with MIT-licensed application source.

This is a credible offer, not a claim that Linty invented the category. There is no exclusive, defensible feature advantage established by this research. Handy, FluidVoice, and OpenWhispr already compete strongly on free local dictation; several paid products already target developers. Linty can earn preference through a focused, dependable experience, useful support, and publicly demonstrated results. “Simpler” and “more reliable” are hypotheses to test, not claims to publish yet. See the [competitor research](2026-09-21-competitors.md).

**The current baseline changes what we should optimize.** The public GitHub API reported 2 stars and 0 forks during this research. Across all 61 release records returned, assets had 1,329 downloads: 67 DMG downloads, 80 updater archive downloads, and 1,182 other asset downloads. The latest release was v0.0.67; its DMG was 12,899,522 bytes, approximately 12.9 MB. These are request counters, not unique people, completed installations, or retained users. The current all-assets badge should not become “1,329 users” in marketing. [Repository metadata](https://api.github.com/repos/shekhardtu/linty), [release records](https://api.github.com/repos/shekhardtu/linty/releases?per_page=100).

The live site responds and has a clear direct download path. Its hero describes general dictation, and the HTML inspected did not contain an `og:image` social-preview image. The README gives substantial space to engine comparisons and synthetic file benchmarks before installation. These are useful technical details, but a short real workflow demonstration and obvious installation path should appear earlier. The existing comparison also omits the closest free alternatives. [Live site](https://linty.ai), [public README](https://github.com/shekhardtu/linty).

**What we can say today, and what still needs proof:**

| Message | Evidence and boundary | Marketing use |
|---|---|---|
| Free app; no account, API key, or subscription required | Documented installation flow and current source | Put near the download button |
| Dictation runs on the Mac after setup | Speech and cleanup paths are local; model downloads and updates use the network | Say “offline after setup,” and demonstrate it |
| Choose a language; Linty prepares the model | Implemented in the language preparation service | Explain the user action; keep model names in technical detail |
| Optional English text cleanup runs locally | English setup prepares S1-mini; other selected languages skip cleanup | Always preserve the English qualification |
| History and personal dictionary | Existing product features | Show recovery and a real recurring term in a demo |
| Small installer | Current release DMG is about 12.9 MB | Disclose model downloads alongside it; avoid implying a 13 MB total installation |
| Faster, more accurate, lighter, or easier than competitors | Not established by a comparative test | Do not publish as fact |
| Better support for Indian accents or Hinglish | Not established by the inspected benchmarks | A possible later research cohort, not an initial promise |

Product evidence: [README](../../README.md), [privacy notice](../../PRIVACY.md), [language preparation](../../src/services/language-preparation.service.ts), [onboarding](../../src/pages/Onboarding.page.tsx), [model attribution](../../src-tauri/licenses/MODELS.md). This was source and documentation research, not a fresh hands-on comparison of the apps.

The cleanup model is S1-mini by Superwhisper. Credit the upstream work when discussing the architecture. The app's MIT license does not replace individual model licenses. Linty's present advantage is the experience it assembles; describing the model as proprietary Linty technology would be wrong.

**Start with a reachable group who have a repeated job.** Recruit 20 Apple Silicon users, ideally 10 developers who already use dictation and 10 who write long prompts or updates but currently type. Include different Mac generations and English accents. Existing dictation users reveal switching costs; new users reveal whether onboarding teaches a useful habit. Select people with a place where speaking aloud is practical. Writers and general Mac productivity users are the next audience if this cohort retains.

Ask each participant to do three ordinary tasks: describe a bug, dictate a prompt or project brief, and write a short update. Observe the initial installation without coaching, then help after documenting the obstacle. Do not ask for private code, prompts, or recordings. The same synthetic sample can be used for a published demo; personal workflow outcomes can be reported without sharing content.

Record where they hesitate: permissions, model download, trigger key, text quality, paste destination, or remembering to use it tomorrow. At day 7 ask how many days they used it, whether it replaced typing or another product, and what made them stop. With 20 people, these findings are directional. Report counts and missing replies, not statistically conclusive percentages.

**Make the first success easier before adding features.** English speech setup is about 500 MB plus roughly 496 MB for cleanup according to current app estimates. That makes first-run waiting more relevant than the DMG size. Measure total setup time, model-transfer time, and time from models-ready to first successful paste separately. If downloads are the main abandonment point, test allowing basic dictation before optional cleanup finishes. If paste reliability is the main problem, prioritize it ahead of new engines or another interface.

For the first 20-person cohort, use these proposed launch gates: at least 14 complete a first useful dictation without live help, at least 8 report use on 3 separate days in their first week, and no unresolved recurring loss-of-text issue appears. Review every unsuccessful attempt. These thresholds are management choices for the experiment, not industry benchmarks or launch guarantees.

**Use one month to earn the first repeat users.** The following schedule assumes roughly 8–10 founder hours each week for distribution and research, plus engineering time for any discovered blockers. If that is too much, cut the number of channels before cutting follow-up with users.

| Period | Work | Output and decision |
|---|---|---|
| Days 1–3 | Record the baseline; prepare one real 30–45 second demo; put compatibility and setup downloads beside the CTA; prepare an accurate social preview | A shareable product someone can understand and install |
| Days 4–7 | Recruit the 20-person cohort through existing relationships and appropriate community invitations; observe installations; collect the first workflow failures | Prioritized activation problems, not a general feature wishlist |
| Days 8–14 | Follow up with the cohort; fix the largest obstacle; publish 2–3 founder demos on existing X/LinkedIn accounts; share a disclosed maker post in one relevant community if its rules allow | First repeat-use evidence and objections in users' own words |
| Days 15–21 | If the gates are met, make one Show HN submission; publish one useful workflow article; approach 5–10 carefully selected small creators or newsletter authors | Qualified visits, useful installs, technical discussion, voluntary stars |
| Days 22–30 | Repeat the best-performing workflow/channel; publish what changed from user feedback; test one comparison page; decide whether Product Hunt is worth preparing | A second cohort and a decision based on usage rather than launch-day traffic |

A launch date is movable if first-use problems remain. Product Hunt can wait until we have a working demonstration, a few permissioned user quotes, and time to respond. A directory listing or a one-day spike alone does not demonstrate product demand.

**Allocate channels by the job they do.** GitHub and Show HN are suited to technical inspection and project discovery. Founder videos and Mac communities let people see the workflow. Articles and comparisons help users who are already considering dictation. A small creator should be selected because their audience uses Macs and writes regularly, not because their follower count is large.

| Priority | Channel | Specific contribution | Primary signal |
|---|---|---|---|
| 1 | Existing relationships and founder accounts | Invite a small trial cohort; show one real task per post | Successful setup and repeat use |
| 1 | GitHub README and Discussions | Put the demo and install first; maintain a clear roadmap and 3 genuinely bounded starter issues | Useful issue reports, contributors, voluntary stars |
| 2 | Relevant Mac/open-source communities | Disclose that we make Linty; ask for feedback on a specific workflow; follow current community rules | Qualified testers and actionable feedback |
| 2 | Show HN | Share the runnable product and personally explain the engineering and tradeoffs | Installs, thoughtful discussion, stars |
| 2 | Small Mac/developer creators | Offer a concise demo and access to the maintainer; ask for independent evaluation | Users who try the demonstrated workflow |
| 3 | Search-oriented articles | Publish one specific tutorial and one fair comparison that includes free alternatives | Sustained qualified traffic over time |
| Later | Product Hunt, wider directories, paid promotion | Broaden reach after activation works | Incremental retained users |

Hacker News currently prohibits generated or AI-edited discussion text and solicitation of votes/comments. The founder should write the submission explanation and replies personally; the copy kit provides preparation topics only for this channel. [HN guidelines](https://news.ycombinator.com/newsguidelines.html), [Show HN guidance](https://news.ycombinator.com/showhn.html).

Do not turn competitor issue trackers into promotional channels. Do not buy stars, exchange stars, or gate installation/features behind a star. A useful contribution, a good demo, and a courteous optional request are more consistent with the community we want.

**Treat stars and usage as separate outcomes.** The user path is: relevant demonstration → compatible Mac visitor → download → successful first dictation → repeated use → recommendation. The contributor path can begin with a technical article or benchmark → repository visit → star, issue, or contribution. Someone can star without installing, and someone can love the app without a GitHub account.

| Metric | Definition | Collection during this month |
|---|---|---|
| New DMG downloads | Change in DMG asset counters across all releases | Public GitHub API snapshot; excludes updater files and metadata; still not unique installers |
| Activation in the cohort | First useful dictation pasted successfully within 24 hours / all cohort participants who begin installation | Consented observation and follow-up; report raw counts |
| First-week repeat use | At least 5 successful dictations across at least 3 distinct days during days 1–7 / cohort participants who begin installation | Voluntary day-7 report or user-reviewed local summary; missing replies reported separately |
| Weekly repeat users in the cohort | People with at least 5 successful dictations over 3 days in that calendar week | Same voluntary method; no claim of whole-product active users |
| New stars | End-of-period minus start-of-period stars | Public repository counter; no attribution to a particular install |
| Recommendations | People who voluntarily shared Linty with another relevant person | Follow-up question; permission before quoting them |

Linty currently has no app usage telemetry. Do not silently add tracking to solve marketing measurement. Begin with a consented panel and aggregate download counters. If a later opt-in diagnostics or usage report is proposed, keep it separate from dictation content and explain the exact data and purpose before collection. Existing website privacy controls block browser fetch/beacon collection; UTM links alone do not create an analytics system. Campaign paths could support coarse host-side counts after the host's handling is understood, but they still would not identify successful installations. See the [current website disclosure](../../PRIVACY.md#website-and-github).

Illustrative 30-day planning targets are 100–300 additional DMG downloads, 50–150 additional stars, and at least 8 of the first 20 participants showing first-week repeat use. These are targets, not forecasts; no reliable conversion baseline exists yet. Reforecast after week 2. Do not derive an install-to-star conversion rate from these unrelated counters. The more important milestone is finding a small group who can explain why they keep using Linty.

If posts get attention but few compatible users try the app, change targeting and the promise. If people download but cannot start, fix onboarding. If they start but do not return, investigate quality, latency, social setting, or weak need. If users retain but stars lag, improve the repository presentation and make a modest optional star request after value has been delivered. If stars grow but usage does not, do not call the GTM successful.

**Create a small set of proof-led assets.** Prioritize one actual workflow video, a focused download page, a useful README, three social creatives derived from the same footage, a founder launch post, one tutorial, and one comparison. A poster alone cannot show that the app successfully captured and pasted someone's words. A real demonstration can become a GIF, screenshot, banner, short post, and article illustration. The [copy and creative kit](2026-09-21-launch-kit.md) contains drafts and production instructions.

**A small companion tool is a later experiment.** The best candidate is a “Type or dictate?” challenge on linty.ai: a sample task, local timers, editable text boxes, and a manual correction-time field. Users dictate using the installed Linty app, compare total task time including correction, and can explicitly export a result card. This measures their own experience; it is not an independent benchmark. It should have no browser speech-recognition engine, no automatic transcript upload, and no misleading preset speedup. Keep it within the existing site/repository. Build it only if the demo does not sufficiently explain the benefit and at least five testers want the comparison. Start with a written challenge first.

A generic AI writing side-app or separate Lite installer would add maintenance and attract a less relevant audience. A browser transcription demo also would not prove system-wide Mac pasting. A second engine, new platform, or smaller model should follow observed adoption barriers, with accuracy and setup tradeoffs tested explicitly.

**The next concrete decision is to run the cohort and record the demo.** Assign one owner to recruitment and follow-up, one to content and channel replies, and one to product fixes; one founder can hold all three roles with scheduled time blocks. Keep no-cost core dictation as the offer for this launch. Revisit sponsorship or paid support once repeat usage and maintenance needs are clearer. Publish only measured results and approved testimonials, and keep “dictation for Mac” beside the Linty name so first-time visitors do not mistake it for a code-linting tool.
