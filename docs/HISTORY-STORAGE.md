# Local transcription history

History is kept **until the user deletes it** by default. There is no record-count limit. Settings → Privacy & storage offers optional 30-day, 90-day, or 1-year retention, JSON export, and clear-all. A finite retention choice shows the number of records it would delete and requires confirmation before applying. Clear-all also requires confirmation; the dictionary and other preferences remain intact.

## Persistence and migration

`src-tauri/src/history_db.rs` owns storage, migration, retention, deletion/Undo and aggregate queries. `src-tauri/src/history.rs` exposes the native commands. The database lives at:

`~/Library/Application Support/ai.linty.desktop/linty-history.sqlite3`

On first access, the complete existing `linty-history.json` and `linty-corrections.json` collections are imported in one SQLite transaction. Original payload fields are preserved, including unknown fields. Missing optional metadata receives backward-compatible defaults. Malformed records, malformed collections, or duplicate IDs abort the whole import and leave the original files intact. Errors surface in the interface with a Retry action.

After the transaction commits, its migration marker prevents reimport. Legacy files are then removed so deleting a transcript does not leave a second application-managed copy behind. Cleanup failure blocks subsequent history operations until it can succeed. A restart between commit and cleanup completes cleanup without reimporting records. This migration cannot recover entries already removed by older versions' 500-record cap.

Older releases read the JSON stores and cannot read this SQLite archive. Reinstalling an older release does not roll back the data migration: it will show an empty history and create a separate JSON store. Export history before a deliberate downgrade; the export is a readable backup, not an automatic restore mechanism. When returning to this release, the already-migrated SQLite archive remains authoritative and legacy JSON files are cleaned up rather than merged, so avoid recording new history in an older release during rollback testing.

Writes update individual records atomically. SQLite uses full synchronization, a rollback journal, secure deletion, and indexed timestamp/ID ordering. Native commands run on blocking workers, keeping disk I/O and archive-lock waits off both the UI thread and async microphone workers. Database connections close after each command. Reset All Data also removes the database and journal. Deleted audio pages are securely cleared and reused by SQLite; the database file does not automatically shrink, avoiding an expensive archive-wide rebuild during use.

## Bounded reads and archive-wide metrics

- History requests 50 records per page; native page sizes are bounded to 100. Search scans saved text and application names/identifiers across the archive, using a literal case-insensitive substring.
- The shared frontend cache holds only the newest 20 records for the tray and other recent-record consumers. It never replaces or truncates the archive.
- Overview, Apps and Privacy & storage query totals across all retained records in their selected period. Dictionary correction totals also use the retained archive. Local-calendar bucket boundaries are generated by `usageBuckets` so charts preserve daylight-saving behavior.
- All time means **all retained history**. Deleting or expiring transcriptions also removes their corrections and statistics; this is not an independent lifetime counter.
- Automatic retention runs at most once every 24 hours. Its last successful run is stored in SQLite, so restarts, focus, wake events, and repeated history access do not bypass the interval. A native timer sleeps until the next due run and works while the window is hidden; launch, wake, and history access also check whether cleanup is due. The default indefinite setting disables the timer. Applying a new retention setting is an explicit immediate cleanup and starts a fresh 24-hour interval.
- Expired entries can remain until the next daily cleanup, or the next launch/wake if Linty is closed or the Mac is asleep. The expiry sweep deletes text, audio, associated corrections, and their statistics in one transaction. Failure rolls the deletion and its schedule back together. Manual deletion and clear-all remain immediate.
- Deletion and expiry clear native menu-bar previews and notify open windows to discard cached history and playback data before refreshing. Playback stops, in-flight reads are cancelled, and Blob URLs are revoked even if the refresh fails. No separate on-disk playback or waveform cache is created. SQLite clears deleted pages and reuses them without an automatic file-shrinking rebuild.

Cleanup exists only inside the running Linty process. It registers no LaunchAgent, daemon, login item, or system scheduled task, and cannot launch Linty or wake the Mac. **Quit Linty** stops it. Closing the main window keeps Linty in the menu bar for dictation, so the daily timer remains available until the app is fully quit.

Individual deletion returns an Undo bundle containing that transcript and its corrections. Restore merges by ID without replacing newer entries. Clear-all and retention changes invalidate older Undo bundles, and expired records cannot be restored. Errors do not falsely report a committed mutation as unsaved when only the subsequent UI refresh fails.

## Optional saved audio

“Save dictation audio” is off by default. See the [audio privacy policy](AUDIO-PRIVACY.md) for consent and data lifecycle behavior. Consent lives in `audio_preferences`, with a version, consent timestamp, and epoch that invalidates in-flight audio after revocation or bulk deletion. Background initialization and history operations publish the epoch into an atomic cache. Starting capture reads this cache without waiting for disk I/O, the database, or retention cleanup. Until initialization succeeds, capture fails closed for audio retention while dictation remains available.

Stopping capture shares the existing sample allocation between transcription and optional history storage (`Arc<Vec<f32>>`). No samples are copied and no WAV is encoded under the recording mutex. `history_save` consumes the matching generation and checks the original consent epoch again, then encodes PCM16 directly into an SQLite incremental blob with a fixed 32 KiB scratch buffer on a blocking worker. No temporary recording or additional whole-file WAV allocation is created. Cancellation, recovery, and completed saves release the pending sample reference. These operations do not load speech models or touch their idle timers.

`transcript_audio` stores WAV blobs under transcript IDs, with a foreign key and cascading deletion. Text and audio commit in one transaction. Transactional triggers maintain audio counts and byte totals, so periodic snapshots do not scan audio rows. Edits preserve audio and immutable transcription snapshots. Transcript deletion, clear, retention pruning, and reset remove associated audio; Undo restores text/corrections only. Audio-only deletion leaves text intact. Saved WAVs are 16 kHz mono PCM16 and preserve the complete captured input without trimming.

The history list loads metadata only. Selecting a transcript loads its recording in sequential chunks of at most 1 MiB and shows the player; playback starts only when the user presses Play. Changing selection cancels after the current bounded read and revokes its Blob URL; unloading the player explicitly stops and detaches audio. Playback accepts at most 64 MiB (roughly 35 minutes of PCM16); larger files remain exportable through the streaming native export, with no full-file allocation in the webview. SQLite blob reads and exports use bounded native buffers.

## Export

Export opens the native save dialog and writes a versioned JSON document containing every retained transcript and correction. It streams from SQLite to a temporary file in the chosen directory, flushes it, and replaces the destination only after writing succeeds. Cancelling makes no changes. The live application data directory cannot be chosen as an export destination. Export does not delete history, send data to a server, or include recordings, credentials, settings, or the dictionary. Importing an export is not currently implemented.

Each saved recording has a separate **Export WAV…** action. It also writes atomically through a native save dialog. Its history entry provides the raw transcript, delivered/edited text, language, model, and timing for future user-directed evaluations. Audio metadata in a JSON archive describes the local attachment at export time; the WAV bytes must be exported separately.

## Verification

- `cargo test --manifest-path src-tauri/Cargo.toml --features local-stt,parakeet`: storage migration beyond 500 records, failed migration rollback/retry, malformed/duplicate input, pagination/search, aggregate reconciliation, delete/Undo, edit preservation, retention expiry, and complete export, plus existing native tests.
- `yarn build` and `yarn test`: TypeScript/build and pure utility tests including local-calendar boundaries.
- `yarn test:audio-history` and `UI_BROWSER=webkit yarn test:audio-history`: opt-in persistence failures, playable synthetic WAV, playback cleanup, audio export/delete, compact layouts, and accessibility. Native tests cover consent revocation/re-enabling, capture generation isolation, atomic audio/text saves, audio-only deletion, Undo, retention, clear, and reset.
- `yarn test:ui` and `UI_BROWSER=webkit yarn test:ui`: synthetic browser tests including a 605-record archive, bounded pages, search past record 500, full totals/export, failure recovery, retention confirmation/Cancel, clear-all and dictionary preservation. The broader suite checks both themes, accessibility, keyboard behavior and the minimum window size.

Tests use temporary databases or synthetic IPC fixtures. They do not read real transcription text or clear real history. Native save-dialog behavior and filesystem errors require a native application pass in addition to browser fixtures.

## Storage benchmark

Run `yarn storage:benchmarks` to display these recorded results in the CLI's Storage report. This command only reads the checked-in measurements; it does not record audio, open your history, or run a new benchmark.

Measured on **19 September 2026**, Apple M3 Pro, 18 GiB memory, macOS 26.5. [Raw results](benchmarks/audio-history-storage-2026-09-19.json).

| Measurement | 1-minute recording | 30-minute recording |
| --- | ---: | ---: |
| Save elapsed time | 3.2 ms | 144.1 ms |
| Save CPU time | 2.8 ms | 123.9 ms |
| Additional peak memory during save | 2.7 MB | 2.7 MB |
| Existing capture buffer | 3.8 MB | 115.2 MB |
| Saved WAV size | 1.9 MB | 57.6 MB |
| Read all audio chunks | 0.4 ms | 224.4 ms |
| Export WAV | 7.4 ms | 49.1 ms |
| Delete recording | 5.9 ms | 130.7 ms |

Each duration was measured once in an optimized process using synthetic PCM and a temporary SQLite archive. Read and export measurements reuse the warm database connection. Additional peak memory is the difference between process high-water marks before and after saving, above the already allocated capture buffer. MB uses decimal units. These results measure storage overhead, not full-app inference, playback, or system-wide GPU/Neural Engine load, and are not a latency guarantee. No microphone, speech models, network, webview, or real history were used.

Saving adds no GPU or Neural Engine inference. Encoding uses a fixed 32 KiB scratch buffer; native reads are bounded to 1 MiB. Saved PCM16 audio uses approximately 1.92 MB per minute; the shared float capture buffer uses 3.84 MB per minute until processing completes.

To reproduce the 30-minute run:

```sh
cargo run --manifest-path src-tauri/Cargo.toml --release --example audio_history_bench -- 1800
```

Use `60` for the one-minute run. The benchmark measures sample sharing, save CPU/elapsed time, peak process memory, bounded reads, export and deletion, then removes its temporary archive.
